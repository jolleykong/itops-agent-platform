## 10:00-10:15 cmdb-sync 频繁 socket hang up 根治（kkv-3.2.2）

### 根因（排除法定位，非 iTop 问题）
- **决定性证据**：同一时刻（相差 5ms）两个不同目标同时 socket hang up
  - `01:25:16.177 Zabbix RPC 失败 (10.240.22.34)`
  - `01:25:16.182 iTop API 失败 (10.0.1.116:8081)`
  - 两个远端不可能同时故障 → 故障点在**发起方进程的 event loop**
- **真因链**：`models/database/mysql/syncDriver.ts` 用 `Atomics.wait` 在主线程轮询等 worker 结果
  → cmdb-sync 把整类 CI 包在**单个事务**里逐条 upsert（Server 1556 条 ≈ 8500 次同步 DB 往返）
  → event loop 冻结 9~12 秒 → keep-alive 连接的 FIN 读不到 → 恢复后报 `socket hang up`
- **排除过的假设（都有实测）**：iTop 服务端慢（手工同查询 164-317ms 全 200）、keep-alive 竞态（40 并发+空闲 7s 全成功）、FD 耗尽（18/1048576）、conntrack（1138/262144）、OOM（125GB 无限制）、opcache/内存（On/1GB）

### 修复
- **P0 传输层重试**（itopClient.ts）：request 拆为「重试外壳 + attemptRequest」；仅重试 ECONNRESET/EPIPE/ETIMEDOUT/EAI_AGAIN/ECONNABORTED 与 5xx；业务错误/4xx 不重试（避免账号锁定）；3 次尝试，退避 300/600ms
- **P1 减少 DB 往返**（cmdbSyncRepository + itopSyncService）：
  - `cmdbSyncLogRepo.insertMany` 多行 INSERT（每批 200 行，timestamp 用 SQL 表达式占位）
  - `syncCIs` 按 200 条分批提交，**批间 `await setImmediate` 让出 event loop**
  - 每批事务内更新 idMap（保留原「数据已写但 idMap 未更新」防护）

用户质疑 cipipe 单独数据库不合理，想共用 CMDB 库并在 CMDB 中独占一层。

**核实结论**：
1. **共用实例有先例**：`iTop/docker/docker-compose.yml:1-7` 注释明确"iTop 与 aiops 共用 `aiops-mariadb` 实例、各自独立 database + 独立 user，只少维护一个数据库进程"。再加 `cipipe` 库同构，零新增进程。
2. **同库加前缀表有实锤故障**：① cipipe `targets/itop_load.py:1058-1078 template_purge_plan()` 扫 `information_schema.COLUMNS WHERE TABLE_SCHEMA=DATABASE()` 且列含 `ci_id/dest_id` 等，`_BENIGN_REF_TABLES=("priv_changeop","priv_sync_replica","priv_change")`，含 ci_id 的 cipipe 表放进 itop 库会被判"阻塞引用"→ 模板机清理失效；② iTop `setup/backup.class.inc.php:330-344` 仅 `db_subname!=''` 才逐表备份，当前为空 → mysqldump 整库 + `--add-drop-database`，恢复连带；③ cipipe 用 `ITOP_DB_USER=root`（cipipe/docker-compose.yml:61），iTop 用 itop 用户，同库无隔离。
3. **iTop 原生替代能力**：表是 `priv_sync_replica`（**无 synchro_replica 表名**）+ `synchro_data_*` + `priv_sync_datasource`；replica 有 `dest_id/dest_class/status/status_last_seen`，`primary_key` 在 staging 表，trigger 用 LAST_INSERT_ID 绑定。8 表中仅 `source_object` 部分可替代（缺 source_id/object_key/payload_hash），其余 7 张无法替代（无 alias/pin/冲突队列/多源证据链）；Tag 模块不在裁剪版（`AttributeTagSet` 代码在但无 Tag 类）。
4. **淘汰语义**：full_load 按 `status_last_seen < 阈值`（import 开始 − periodicity）判 obsolete，非"replica 缺席"；引擎只查自己 DS/replica，不扫 information_schema，不会清理同库 cipipe 表。
5. iTop setup/upgrade 不 DROP 未知表/列（setup 目录零 DROP TABLE，全局无 DROP COLUMN）；`synchro_data_` 是保留前缀。

**评审稿**：`output/CIPipe数据库归属决策评审-2026-11-27.md`，结论 F1–F6：共用 `aiops-mariadb` 实例 + 独立 `cipipe` database + 独立 user；禁止同库前缀表；"CMDB 独占层"=字段级隔离+`data_layer` 标记，非搬表。零源码改动，三仓库干净。

## 15:01-15:03 消费端读取边界核实（只读）

用户问：aiops 等 CI 消费端从 iTop 读，还是 iTop+cipipe 混合读。

**核实结论**：
1. **aiops 从未读 cipipe**（交叉验证）：全仓 backend/src 中 `cipipe` 仅 1 处注释（`itopSyncService.ts:256`）；无第二 DB 连接、无 cipipe API 调用、无 `snapshot-server.db` 引用。CI 主数据单一读 iTop。
2. **两条 iTop 读取路径**：① `itopSyncService.ts:179` 的 `itopClient.getObjects()` 是唯一批量取数入口，30min 周期（默认 `ITOP_SYNC_INTERVAL_MINUTES`），按 iTop 数字 id 对账（`itop_id_map`），退役/obsolete 反向清理（L255-280）；② `ciChainService.ts` 看板关系链按需实时查 iTop（按 name/friendlyname）。看板主视图读本地 `dc_rack_slots`（`slotsRepo.ts:79` 纯本地 JOIN），不读外部。
3. **已有混合读先例（非 cipipe）**：`ciChainService.ts` = iTop 实时 + 本地 servers + Zabbix 派生；L591 本地 IP 补 iTop managementip 空值；L741-755 iTop 不可达时 `source:'local'` 静默降级；`serverAssetCategory.ts:4` 注释 servers 表混合来源。风险：字段补全拼出任一源都不存在的记录、静默过期、U 位双权威。
