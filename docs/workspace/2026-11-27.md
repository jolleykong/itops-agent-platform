## 10:00-10:15 cmdb-sync 频繁 socket hang up 根治（kkv-3.2.2）

### 根因（排除法定位，非 iTop 问题）
- **决定性证据**：同一时刻（相差 5ms）两个不同目标同时 socket hang up
  - `01:25:16.177 Zabbix RPC 失败 (10.240.22.34)`
  - `01:25:16.182 iTop API 失败 (10.0.1.116:8081)`
  - 两个远端不可能同时故障 → 故障点在**发起方进程的 event loop**
- **真因链**：`models/database/mysql/syncDriver.ts` 用 `Atomics.wait` 在主线程轮询等 worker 结果
  → cmdb-sync 把整类 CI 包在**单个事务**里逐条 upsert（Server 1556 条 ≈ 8500 次同步 DB 往返）
  → event loop 冻结 9~12 秒 → keep-alive 连接的 FIN 读不到 → 恢复后报 `socket hang up`
- **排除过的假设（都有实测）**：iTop 服务端慢（手工同查询 164-317ms 全 200）、keep-alive 竞态（40 并发+空闲 7s 全成功）、FD 耗尽（18/1048576）、conntrack（1138/262144）、OOM（125GB 无限制）、opcache/内存（On/1GB）

### 修复
- **P0 传输层重试**（itopClient.ts）：request 拆为「重试外壳 + attemptRequest」；仅重试 ECONNRESET/EPIPE/ETIMEDOUT/EAI_AGAIN/ECONNABORTED 与 5xx；业务错误/4xx 不重试（避免账号锁定）；3 次尝试，退避 300/600ms
- **P1 减少 DB 往返**（cmdbSyncRepository + itopSyncService）：
  - `cmdbSyncLogRepo.insertMany` 多行 INSERT（每批 200 行，timestamp 用 SQL 表达式占位）
  - `syncCIs` 按 200 条分批提交，**批间 `await setImmediate` 让出 event loop**
  - 每批事务内更新 idMap（保留原「数据已写但 idMap 未更新」防护）
